# LLMモデル比較実験レポート（gemma3:4b / gemma3:12b）

> **実施日**：2026-10-01（Ollama 0.35.0）
> **比較対象**：gemma3:4b（現行）、gemma3:12b（候補）。gemma3:27b は計測していません（§9）。
> **結論の要約**：12B に変えると**タスク分解の網羅性と JSON の安定性は明確に上がります**。しかし、処理時間は **1ジョブあたり約8〜12倍（35〜60分）** になり、**依存関係の生成は6回中5回で0件（タイムアウト）** でした。さらに**未割当が大幅に増えました**（タスクの約70〜80%）。このため、現在のコード・設定のままでは本番には採用できません。本番設定は gemma3:4b のまま維持しています。

**表記ルール**

- **【実測】** … 今回の計測で得た値
- **【推測】** … 実測から推論した内容（未検証）
- 値は、特記がない限り **3回の平均（最小–最大）** です。

## 4. 速度比較

### 4.1 要素ごと【実測】

| 項目 | gemma3:4b | gemma3:12b | 12B / 4B |
|---|---:|---:|---:|
| モデルロード時間（コールドスタート） | 5.6〜7.9秒 | 12.3〜15.5秒 | 約2倍 |
| 生成速度（output token/秒） | 58〜61 | 6.9〜7.7（依存段階は 5.3〜6.3） | **約1/8.6** |
| output 1トークンあたりの時間 | 約16ms | 約130〜145ms | 約8.6倍 |
| プロンプト処理速度（token/秒） | 2,200〜2,900 | 350〜410 | 約1/6.5 |
| Requirements 1回あたり | 3.6秒（A）／7.8秒（B） | 28.6秒／52.0秒 | 約7〜8倍 |
| Tasks 1回あたり | 8.3秒／8.9秒 | 71.5秒／76.7秒 | 約8.6倍 |
| Dependencies 1回あたり | 49秒／78秒 | 約299秒（ほぼ全回タイムアウト） | 計測不能（打ち切り） |
| **Pipeline 全体** | 3分9秒／7分32秒 | 39分15秒／57分41秒 | **A：12.5倍、B：7.7倍** |

### 4.2 読み取れること

- 1回の呼び出しが遅くなるのは、ほぼ**生成速度の差（約8.6倍）** によるものです。出力トークン数は両モデルでほぼ同じ（Tasks 1回あたり 450〜510トークン）です。
- 12B では**要件の数が約1.5〜1.8倍に増える**ため、Tasks の呼び出し回数も増えます（A：11回→19回、B：20回→30回）。そのため Tasks 段階は 13〜15倍になりました。
- B で全体の倍率が 7.7倍と小さく見えるのは、12B の依存関係の段階が **300秒×3回で打ち切られている**からです。打ち切りがなければ、さらに長くかかったと考えられます【推測】。
- Assignment・Validation・Finalize は両モデルとも1秒未満で、モデルの影響はありません。

## 6. JSON 安定性比較【実測】

各実行の LLM 呼び出しをすべて記録した結果です（3回の合計）。

| 項目 | 4b / A | 12b / A | 4b / B | 12b / B |
|---|---:|---:|---:|---:|
| HTTP 試行回数（全段階） | 55 | 84 | 84 | 114 |
| JSON 解析の失敗 | 1（依存、出力打ち切り） | 0 | **8**（依存、すべて `done_reason=length`） | 2（依存、`done_reason=length`） |
| スキーマ不正（dict でない等） | 0 | 0 | 0 | 0 |
| 期待キーの欠落 | 4（タスク） | 0 | 9（タスク） | 0 |
| 空の `{}` | **4**（タスク） | **0** | **9**（タスク） | **0** |
| タイムアウト（300秒） | 0 | **7**（依存） | 0 | **7**（依存） |
| Ollama HTTP エラー | 0 | 0 | 0 | 0 |
| リトライ | 1 | 7 | 8 | 9 |
| タスク0件になった要件（1回あたり） | 1.3 | 0 | 3.0 | 0 |
| 依存関係が0件の実行 | 0/3 | 2/3 | 2/3 | 3/3 |

- **Requirements 段階は、両モデルとも全呼び出しが正常**でした。
- **4B の `{}` 問題は再現しました。** タスク分解で、有効な JSON の `{}`（出力2トークン）が返ります。`call_llm_json` は dict なので成功として扱い、**リトライせず**、その要件のタスクが0件になります（`DECOMPOSITION_ERROR`）。12B では84回＋114回の呼び出しで一度も起きませんでした。
- **4B の依存関係の失敗は、出力の打ち切りが原因**です。
  - 入力B ではプロンプトが 3,300〜4,100 トークン、出力が 4,100〜5,200 トークンに達し、合計が `num_ctx=8192` を超えて `done_reason=length` となり、JSON が途中で切れました。
  - 3回試しても毎回同じ長さで失敗するため、リトライでは回復しません。
- **12B の依存関係の失敗は、速度が原因**です。約6トークン/秒では、1,800トークン程度の出力でも300秒の上限に届きます。
  - 12B / B の Run 2 では、2回が `done_reason=length`（出力1,574トークン、プロンプト約4,400トークン）で終わりました。合計が 8192 に届いていないのに length になった理由は**未確認**です。
- 参考：Ollama 0.34.4 で先に行った 4B の6回でも、同じ傾向でした。
  - タスク分解の `{}`：1回あたり1〜5回
  - 入力B の依存関係：2/3回が0件（1回は `{}`、1回は3回とも length）
  - Ollama の HTTP 500 が1回

## 8. 4B → 12B の変化（今回一番知りたかったこと）

### 質問1：タスク分解・依存関係の品質は明確に向上するか？

| 観点 | 結果 | 確度 |
|---|---|---|
| タスク分解の網羅性 | **向上**。全要件からタスクが生成され、仕様項目の網羅も 6/6 回で満点。4B は `{}` による欠落で、1回あたり1〜3件の要件（仕様項目）が抜けた | 3回×2入力で一貫 → 高い |
| JSON の安定性（Requirements / Tasks） | **向上**。`{}`・キー欠落が 0 件（4B は1回あたり1〜4件） | 高い |
| unknown skill | **大幅に減少**（26〜40% → 1〜3%） | 高い |
| タスクの具体性 | 向上したものが多い（管理者の後任指定・トークン保護などを具体的な作業に分解）。一方で、**重複（100件あたり 27 → 43〜60ペア）と仕様外のタスク（例：フロントエンド UI）が増えた** | 中（目視は Run 1 のみ） |
| 依存関係 | **評価不能〜悪化**。6回中5回が300秒のタイムアウトで0件。成功した1回は 4B より自然に見えた | 成功1回のみ → 低い |
| 割り当て結果 | **悪化**（未割当 21〜23% → 70〜82%）。原因はモデルの品質ではなく、スキル名の表記とメンバーのスキル名が一致しないこと | 高い |

**結論**：タスク分解は「明確に向上」と言えます。依存関係生成は、**今の 300 秒のタイムアウトでは 12B で完了しない**ため、向上したかどうかを判断できません。

### 質問2：処理時間は何倍になるか？

- **1回の呼び出し：約8.6倍**（生成速度 60 → 7 トークン/秒）
- **パイプライン全体**
  - 入力A：3分 → 39分（**約12.5倍**）
  - 入力B：7.5分 → 58分（**約7.7倍**。依存の段階が打ち切られた状態での値）

### 質問3：RTX 4050 Laptop / RAM 32GB で 12B は実用的に動くか？

- **動作はする**：6回すべてで異常終了なし、OOM なし。
- **実用的な速度ではない**：
  - 1ジョブに35〜60分かかる
  - 依存関係の段階がタイムアウトで失敗する
  - RAM 使用量が 28GB に達する
  - GPU に載るのは約37%

## 9. 12B → 27B の変化

- **計測していません。** 12B の結果（GPU に載るのは約37%、生成速度約7トークン/秒、依存関係の段階がタイムアウト）を踏まえ、実験担当者の判断で 27B の計測は行わないことにしました。
- **以下はすべて【推測】で、実測ではありません。**
  - 27B はファイルサイズが約17GB で、6GB の VRAM に載るのは2割程度と考えられます。
  - 12B より生成速度はさらに下がると考えられ、依存関係の段階だけでなく、Tasks 段階でも300秒のタイムアウトに届く可能性があります。
  - RAM は 32GB の上限に近づくと考えられます。
- ダウンロードは途中で中止しました。27B はインストールされていません（`ollama list` に無い）。

## 11. 発見した問題

1. **`{}` が成功扱いになる**（4B）
   - `call_llm_json` は、期待キーが無い dict（`{}`）でもリトライしません。そのため要件のタスクが静かに0件になります（`services/pipeline/llm_json.py`）。
2. **依存関係を1回の呼び出しで作るため、コンテキストが溢れる**（4B）
   - プロンプトと出力の合計が `num_ctx=8192` を超え、`done_reason=length` で JSON が切れます。毎回同じ長さで失敗するので、リトライは無駄になります（`pipeline/dependencies/proposer.py`）。
3. **300秒のタイムアウトが大きいモデルに合っていない**（12B）
   - 依存関係の段階が 300秒×3回＝約15分かかったうえで失敗します。
4. **スキル名の表記ゆれで未割当が急増する**（12B）
   - チームスキル語彙をプロンプトに渡していても、12B は「テスト計画」「コミュニケーション」などの独自の名称を使います。スキル照合は完全一致です。
5. **4B の依存関係が ID の連番チェーンになる**
   - 85〜100% が `TASK-i → TASK-(i+1)` の形でした。
6. **仕様に反するタスクが生成される**
   - 「ユーザー登録機能は不要」とあるのに、登録のタスクが生成されました（4B で1回、12B で1回）。
7. **メンバーデータのスキル名が壊れている**
   - 入力に使ったメンバーのスキルに `"DevOpsAWS (ECS"`、`"S3)"` があります。画面のスキル入力（`名前:レベル` をカンマで区切る形式）で、`DevOps/AWS (ECS, RDS, S3)` がカンマの位置で分割されたと考えられます【推測】。照合に影響するので、デモ前に修正してください。
8. **Validation が全実行で `error`**
   - 両モデルとも critical が0になった実行はありません。重複候補や未割当があれば必ず critical / warning になるため、`status` だけではモデルの良し悪しを区別できません。
9. **実験中に Ollama が自動更新された**
   - 0.34.4 → 0.35.0。0.34.4 で計測した 4B の6回と 12B の途中までの記録は、参考値として別に保存しました。本レポートの比較表はすべて 0.35.0 の値です。
10. **取り残されたジョブ**
    - 実験前、DB に `running` のまま止まったジョブ（5db89813、qwen3:8b で実行されたもの）がありました。バックエンドの停止時に回収されない、既知の制約です。

## 13. 結論

- **gemma3:4b → 12b でタスク分解の品質は明確に向上しました。**
  - 全要件がタスク化され、仕様項目の網羅は満点、`{}` は0件、unknown skill は約1/10になりました。
  - これは 3回 × 2入力で一貫した結果です。
- **その代償として、処理時間は約8〜12倍（1ジョブ35〜60分）になりました。**
- **依存関係の生成は、12B では現在の300秒のタイムアウトで完了しませんでした**（6回中5回が0件）。そのため品質は比較できていません。
- **スキル名の表記の違いにより、未割当が 21〜23% から 70〜82% に増えました。**
- この PC（RTX 4050 Laptop / 32GB）で 12B は「動くが、実用的な速度ではない」と判定します。GPU に載るのは約37%、RAM は 28GB に達します。
- 27B は計測していません。
- **本番は gemma3:4b のまま維持します。** 次の一手は、モデルを替えることではなく、§12 の改善を先に行うことです。特に効果が大きいのは次の2つで、どちらも 4B の現在の弱点を直接改善します。
  - `{}` をリトライ対象にする
  - 依存関係の生成を分割する

### 付録：データの保存場所

実験スクリプトと生データ（全呼び出しのメトリクス、ハードウェアのサンプル、各段階の出力 JSON）は、作業用の一時フォルダにあります。一時フォルダはセッション終了後に消える可能性があるため、残す場合はリポジトリへのコピーが必要です。

- `run_one.py`：1回分の実行と計測
- `driver.py`：一括実行
- `analyze.py`：集計
- `coverage.py`：網羅チェック
- `summary.json`、`summary_runs.json`、`coverage.json`：集計結果
